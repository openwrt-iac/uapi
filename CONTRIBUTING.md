# Contributing to uapi

Thanks for considering a contribution. This page covers the dev loop; the deeper architecture / design / wire-contract docs are linked at the bottom.

## Environment

You need a Linux host with:

- `ucode` 1.0+ (the language runtime). Available in most distros as `ucode` or `libucode`; OpenWrt ships it natively.
- `make`
- `git`
- For integration tests: `qemu-system-x86_64`, `openssh-client`, `wget`, plus ~2 GB free disk for the OpenWrt VM image.
- For building the APK locally: the OpenWrt SDK (downloaded on demand by `make stage`; ~400 MB).

uapi does NOT need `node`, `python`, or any JS toolchain. The OpenAPI spec is generated by a ucode script, not a JS one.

## Dev loop

```sh
make test                # lint + 600+ unit tests + coverage gate (~5 sec)
make openapi             # regenerate build/openapi.json from src/resources/*.uc
make stage               # stage files into build/openwrt/uapi/files/ for APK packaging
make help                # full target list
```

Run `make test` before every commit. The coverage gate fails the build if direct unit-test coverage drops below 80% of lib exports, so new helpers need a focused test.

For integration tests against a real OpenWrt VM:

```sh
make vm-setup            # one-time: downloads + verifies the OpenWrt 25.12 image
make vm-start            # boots the VM in the background
make test-integration    # runs tests/integration/*.sh against the VM
make vm-stop             # shuts the VM down
```

CI runs all of this automatically on every PR. Locally you can stop at `make test` for most changes.

## What kinds of changes are welcome

- **New curated resources.** Follow [`docs/adding-a-resource.md`](docs/adding-a-resource.md). The pattern is uniform; expect about an hour for a typical config type.
- **Schema-property additions** to existing resources (a uci option exists but uapi does not surface it yet).
- **Bug fixes** with a regression test that fails before the fix and passes after.
- **Documentation improvements**, especially anything that lowered your learning curve.
- **Test coverage** for code paths the existing suites miss.

For larger changes (new wire features, new endpoints, anything touching the auth or transaction model), open an issue first so we can talk through the design. uapi is small on purpose; not every nice idea earns its keep against the [zero-bloat constraint](CLAUDE.md#architectural-principles-non-negotiable).

## Commit and PR style

- **One-line commit subjects.** Conventional-commit prefix is fine but not required (`fix:`, `feat:`, `refactor:`, `docs:`, `test:`, `harden:`). Multi-paragraph bodies are welcome on substantive commits.
- **No em-dashes anywhere** (code, comments, docs, commit messages). The lint job will catch them.
- **No AI-narrator comments.** See [`CLAUDE.md` "Avoid AI slop"](CLAUDE.md#avoid-ai-slop-high-importance) for the bar. A good test: "would a senior engineer reading this ask 'why is this here?' and get a non-obvious answer?" If no, delete the comment.
- **Tests stay green.** PRs that break `make test` will not be merged. If the coverage gate trips on new helpers, add tests rather than adjusting the threshold.
- **Resource changes regenerate `build/openapi.json`**. Commit the regenerated file alongside the resource module.

PRs don't need to be GPG-signed; only release tags do (and only the maintainer cuts those).

## Codebase tour

```
src/
  main.uc                # uhttpd-mod-ucode entry point; dispatcher
  raw.uc                 # /raw/<package>/<id> passthrough handler
  lib/                   # shared helpers (auth, transaction, errors, ids, ...)
  resources/             # one module per curated resource (firewall.rules, system, ...)
build/
  gen_openapi.uc         # OpenAPI generator (reads src/resources/*.uc + ENDPOINTS table)
  openapi.json           # generated; committed; CI gates against drift
  openwrt/uapi/          # OpenWrt package skeleton; staged from src/ by `make stage`
  sdk.sha256             # pinned OpenWrt SDK checksums (multi-arch)
cli/
  uapi-token             # CLI for token mint / list / revoke
docs/                    # operator + contributor docs (you are here)
tests/
  unit/                  # ucode unit tests; run by `make test`
  integration/           # shell + curl tests; run by `make test-integration` in QEMU
  harness.uc             # ~100-line test harness (describe / it / assert_*)
  coverage.uc            # structural test-coverage inventory
web/                     # static site published to gh-pages (landing page + Redoc viewer)
```

## Friction-points worth knowing before you start

- **[`docs/ucode-quirks.md`](docs/ucode-quirks.md).** Read this before you write your first patch. ucode is OpenWrt's native scripting language and looks like JavaScript but has surprising differences (no function hoisting, no `try/finally`, strings not indexable). Each item on the list has cost a debug round-trip on this project.
- **[`docs/concurrency.md`](docs/concurrency.md).** uapi runs inside `uhttpd-mod-ucode`'s fork-per-request CGI model, not a long-lived process. That changes what's safe to cache and what's not.
- **[`docs/architecture.md`](docs/architecture.md).** Atomic-transaction recipe, ETag derivation, scope tree, snapshot/restore. The "why" for the design choices.

## Where to get help

- Open a [GitHub Discussion](https://github.com/openwrt-iac/uapi/discussions) for design questions.
- File an [issue](https://github.com/openwrt-iac/uapi/issues) for bugs. Include the router's OpenWrt version, the uapi version (`cat /usr/share/uapi/VERSION`, or the `version` field of `GET /healthz`), and the syslog excerpt around the failure if you have it.
- For security-sensitive reports, see [`docs/security.md`](docs/security.md).
